# P02: закрепление пилотного корпуса, инженерный слой

Статус: подготовлена схема и проверяемые ограничения для будущего пилота.
Реальный русский корпус не импортирован. Паспорт
[`pilot_contract.yaml`](pilot_contract.yaml) остаётся черновиком: владелец,
доступ, права, закрытая выборка, оборудование и пороги блока 1 не утверждены.
Этот код не означает приёмку P01, P02 или закрытую проверку P05.

## Разделы и расположение данных

Новый API `text_factors.observations.pilot_corpus` использует пять явных
разделов: `train`, `development`, `calibration`, `sealed_test`, `future_stream`.
Предыдущий английский эксперимент GUM продолжает работать со своей схемой
`train` / `validation` / `test`; старые JSON и команды не переименованы.

Архив, передаваемый в `freeze_pilot_corpus`, содержит **только первые три**
раздела. Для `sealed_test` и `future_stream` другой хранитель передаёт
хешированные записи: SHA-256 байтов источника, SHA-256 нормализованного текста
и commitment группы. Ни исходного текста, ни меток, ни ID упоминаний этих
разделов в пилотном manifest нет. `future_stream` пока может иметь пустой
список, `sealed_test` требует непустую запись. Закрытый архив должен физически
находиться вне пути и прав доступа процесса обучения; эту границу устанавливает
оператор хранилища, Python API сам не создаёт права доступа к файлам.

Хеш текста позволяет проверить точное совпадение и может раскрыть короткий
предсказуемый текст при переборе. Поэтому даже записи без текста являются
**закрытым внутренним артефактом**; не публикуйте их в репозитории. Для групп
используйте отдельные случайные непрозрачные UUIDv4, созданные
`uuid.uuid4()`, и сохраняйте связь с документами только у владельца данных.
Программа проверяет формат UUIDv4, но не может доказать качество генератора.
Именованные ID вроде `project-task-1` отвергаются: обычный SHA-256 такого ID
не скрывает название. Хеши и fingerprint manifest **не являются цифровой
подписью**: тот, кто может изменить manifest, может пересчитать fingerprint.
Хранитель фиксирует его SHA-256 во внешнем неизменяемом журнале перед
обучением и передаёт разрешение на единственный запуск закрытой оценки отдельно.

## Импорт, разметка и дубли

Используется существующий `ObservationArchive`: исходные UTF-8 байты и
координаты Unicode/UTF-8 остаются неизменными, исходная версия и версии
привязок закрепляются, повторный импорт тех же данных возвращает тот же ID
и версию. В metadata каждой открытой версии нужны строки `origin`, `language`,
`rights_evidence_reference`, `access_policy_reference`,
`annotation_policy_reference`, `grouping_evidence_reference` и объект
`annotation_coverage` со значениями `mentions` и `identity` из
`complete` / `partial` / `unknown`. Формальное наличие ссылки не подтверждает
права само по себе. Для train требуется `mentions: complete`: иначе
неразмеченные интервалы нельзя использовать как отрицательные примеры.

Проверка `normalized_sha256` применяет Unicode NFKC → casefold → NFKC,
сводит последовательности пробельных символов к одному пробелу и берёт
SHA-256 UTF-8. Она используется **только для контроля пересечений** и не
изменяет байты, координаты, регистр или написание источника. Между любыми
двумя разделами отвергаются одинаковая семейная группа, исходный хеш или
нормализованный хеш. Внутри закрытого раздела также отвергаются повторные
записи с совпадающим raw/normalized/group digest. Семейство документа и
вся история связанной задачи должны получать **один** group ID; ревизии
одного семейства могут оставаться внутри одного открытого раздела.

Проверка близких перепечаток остаётся внешней процедурой. Для freeze обязателен
структурированный `near_duplicate_review` со списком всех group commitments,
ссылкой на журнал screening, точным SHA-256 списка групп и подозрительных пар,
ID проверяющего и ссылкой на проверку каждой пары. Все пары из
`candidate_pairs` должны иметь одноимённое решение в `reviewed_pairs`.
Решения `related`, незакрытая пара или отсутствие журнала останавливают
заморозку. Запись `independent` — **свидетельство решения человека**, а не
алгоритмическое доказательство, что список подозрительных пар полный.
Реальный журнал и происхождение групп проверяет владелец данных.

## Входная спецификация и train API

```json
{
  "schema": "ai2-pilot-corpus-assignments-v1",
  "assignments": [
    {"source_id": "OPEN_SOURCE_ID", "source_version": 1, "split": "train"}
  ],
  "restricted_receipts": {
    "sealed_test": {"members": [{
      "source_sha256": "<64 lowercase hex>",
      "normalized_sha256": "<64 lowercase hex>",
      "group_commitment": "<64 lowercase hex>"
    }]},
    "future_stream": {"members": []}
  },
  "near_duplicate_review": {
    "status": "completed",
    "reviewer": "<independent reviewer ID>",
    "method": "<screening method>",
    "evidence_reference": "<review journal>",
    "screening_reference": "<candidate screening journal>",
    "screening_sha256": "<64 lowercase hex>",
    "reviewed_group_commitments": ["<sorted commitments of all groups>"],
    "candidate_pairs": [],
    "reviewed_pairs": []
  }
}
```

`screening_sha256(groups, candidate_pairs)` вычисляет хеш того же
канонического JSON, что принимает валидатор; пары в нём упорядочены по
двум digest. Для каждой подозрительной пары `reviewed_pairs` добавляет те же
`left`/`right`, `decision: independent` и `evidence_reference`.

```bash
text-factors observations freeze-pilot --archive open.sqlite --data pilot-assignments.json --output pilot-manifest.json
text-factors observations validate-pilot --archive open.sqlite --data pilot-manifest.json
```

При подключении обучателя передавайте результат
`pilot_training_view(open_archive, pilot_manifest)`: он содержит только
закреплённые `train` тексты и существующие привязки с их annotator/evidence.
Привязка с `selected_id: null` сохраняет статус `unresolved`/`ambiguous` и не
даёт отрицательной пары. Отсутствие связки также не означает `different`.
Из `selected_id` нельзя создавать новые отрицательные пары без утверждённой
политики разметки; явные проверенные метки перечислены ниже. Старый GUM-обучатель
использует свою явно полную англоязычную разметку и не читает P02 manifest.

Явные метки пар теперь сохраняются через
`ObservationArchive.annotate_identity_pairs` со схемой
`ai2-open-identity-pairs-v1`. Один вызов фиксирует окно `start`/`end` исходной
версии, список `mention_ids`, `coverage: complete` / `partial` / `unknown`,
`policy_reference`, `annotator`, `evidence`, `expected_version` и список
`pairs` с метками `same` / `different` / `unknown`. Координаты Unicode
ссылаются на оригинальный текст; каждое упоминание обязано принадлежать этому
окну и версии источника. Окна одного документа не пересекаются. Версии
областей и пар только добавляются; исправление даёт новую версию с явным
`expected_version`, старые замороженные версии доступны для повторной проверки.
Существующие архивы SQLite v1 получают только дополнительные таблицы и
`user_version=2` при открытии, исходные версии и ID не меняются.

`complete` требует перечислить **каждое существующее упоминание** окна и
каждую возможную пару перечисленных упоминаний. Даже при полном перечислении
метка `unknown` остаётся неизвестной. `partial` допускает пропущенные пары,
которые также остаются неизвестными. `unknown` допускает только метку
`unknown`; **из отсутствия записи никогда не выводится `different`**.
Сочетание `same(A,B)`, `same(B,C)` и явного `different(A,C)` противоречит
транзитивной идентичности и отклоняется. Новые пары из цепочек `same` не
генерируются. При заморозке и повторной проверке явные метки сопоставляются
с **закреплёнными версиями** выбранных `selected_id`: `same` требует равенства,
`different` — различия, если обе стороны имеют известные ID. Если хотя бы
одна привязка неизвестна, она не создаёт скрытое `different`. Исправление
привязки или пары создаёт следующую версию, прежний manifest остаётся
проверяемым по своим версиям. Пары этого формата принадлежат одной версии
**одного** документа; для связей между документами или версиями одного
семейства нужен отдельный проверенный протокол. Это пока ограничивает P04.
Фраза `complete` ограничена зафиксированным набором упоминаний: при появлении
новых упоминаний заморозка свежего manifest потребует пересмотреть полноту.
Если source metadata объявляет `annotation_coverage.identity: complete`,
требуется полная область на весь текст; при `partial`/`unknown` границы
показывают локальную полноту, не подменяя общую.

`freeze_pilot_corpus` фиксирует ID и версии областей только для открытых
документов. `pilot_training_view` возвращает для `train` массивы
`identity_scopes` и `identity_pairs`, включая происхождение каждой метки.
Результат содержит только **явно** записанные пары: `same` и `different`
можно передавать в обучение согласно политике пилота, `unknown` и пропуски
нельзя считать отрицательными. Области и пары `development`, `calibration`,
`sealed_test` и `future_stream` в тренировочный view не попадают. Manifest
v1, замороженный до появления нового поля, продолжает валидироваться с
пустыми областями: отсутствующие пары считаются неизвестными. Даже при
старой metadata `identity: complete` train-view отдаёт эффективное
`annotation_coverage.identity: unknown` и `pair_supervision:
explicit_pairs_only`: старые привязки не доказывают полный перебор пар.
Новый freeze с metadata `identity: complete` требует полную область.

Пример добавления внешней проверенной пары после обычного `annotate`:

```json
{
  "schema": "ai2-open-identity-pairs-v1",
  "source_id": "OPEN_SOURCE_ID",
  "source_version": 1,
  "start": 0,
  "end": 100,
  "coverage": "partial",
  "policy_reference": "internal:identity-policy-v1",
  "annotator": "reviewer-id",
  "evidence": "internal:pair-review-17",
  "mention_ids": ["MENTION_ID_A", "MENTION_ID_B"],
  "pairs": [{
    "left_mention_id": "MENTION_ID_A",
    "right_mention_id": "MENTION_ID_B",
    "label": "unknown"
  }],
  "expected_version": 0
}
```

```bash
text-factors observations annotate-pairs --archive open.sqlite --data pair-review.json
text-factors observations identity-scopes --archive open.sqlite --source OPEN_SOURCE_ID --version 1
```

Это именно контракт для будущих разрешённых данных, а не готовая разметка
реального пилота. Перед обучением нужно проверить качество людей и политику
разметки независимо от структурных ограничений схемы.

Для реальной приёмки P02 нужны подтверждённые документы и права, инструкция
разметки, группировка задач/редакций, независимая ревизия подозрительных
перепечаток, физически отделённый закрытый набор и зафиксированные manifest
с внешним подтверждением fingerprint. Здесь есть только проверяемая схема и
тесты на синтетических фрагментах.
