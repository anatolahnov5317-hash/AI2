# P16–P17: версии, журнал задач и оперативный доступ

Статус на 2026-09-23: **инженерная проверка на придуманных данных**, не
разрешение на пилот и не подтверждение соблюдения прав на реальные документы.
Блок 1 оставлен условной основой; закрытый набор не применялся.

## Реализованный контракт

- `bundle.py`: атомарная запись одного JSON комплекта engine, обученного
  `OpenSemanticModel`, `ContextRegistry`, конфигурации `CompositionalEncoder`,
  версии модели, корпуса и политики. Пиннинг и SHA-256 тела/компонентов,
  отказ при несовпадении версии/ширины кодирования/модели фактов. Прямая
  загрузка старого state v1 не выдаётся за совместимый bundle: доступна
  явная `migrate_v1_state` с обученным semantic artifact и требуемыми версиями.
- `storage.py`: отдельная SQLite база `OperationalStore` с grant по principal и
  scope, tombstone пары `(source_id,version)` для отдельной редакции и
  `revoke_source_family(source_id)` для всех имеющихся и будущих редакций,
  идемпотентным request ID + fingerprint и журналом `pending/complete/published`.
  Журнал сохраняет только SHA результата, без выдержек и текста. Неподходящий
  повтор ID отвергается. При переходе формата authority v2→v3 оба вида
  tombstone остаются независимыми от отката модели.
- Выдача: `publish_answer` в `BEGIN IMMEDIATE` сверяет epoch, текущую версию
  состояния, pending claim IDs, grants, tombstones, все корни, SHA/область
  каждого фрагмента в `ObservationArchive`, состояние engine и точный текст
  цитат. Текст ответа обязан совпадать с конкатенацией проверенных цитат;
  неподготовленные фразы этой функцией не публикуются. Отзыв, успевший
  зафиксироваться до этой транзакции, блокирует выдачу. Повтор ранее принятого
  запроса заново проходит живую проверку доступа.
- Пересмотр: `start_revision` в той же SQLite блокировке атомарно увеличивает
  `revision_epoch` и записывает затронутые claim IDs до обработки. Подготовленный
  на предыдущем epoch ответ отвергается даже после завершения ревизии. До
  `finish_revision` затронутые факты остаются закрыты; независимый факт может
  выдаваться с новой эпохой и всё ещё действующей версией engine. После сбоя
  pending сохраняется и блокирует выдачу. `finish_revision` требует совпадения
  сохранённого epoch и вызывается только после долговечной записи нового
  состояния; неполное/неразрешённое задание нельзя завершать.
- Откат: `load_bundle(..., authority=OperationalStore(...))` накладывает
  tombstones из отдельного журнала поверх старой модели. После загрузки
  оператор явно вызывает `bind_state_version` с текущей эпохой; этот метод
  меняет активную версию, но не журнал отзывов. Источник из старого bundle
  остаётся заблокирован; независимый источник может работать.

## Проверка

`tests/test_p16_p17_operational_storage.py`: **12/12** профильных тестов.
Они проверяют миграцию v1→v2 с удалением старого текста задачи, согласованную
загрузку, подменённые хеши и состояния, отсутствие повторной записи, живые
grant/revoke, поток с отзывом между подготовкой и выдачей, переход epoch при
старте ревизии, независимую выдачу и откат старого bundle поверх отзывов.
Отдельно проверены отзыв всего source ID до импорта его второй редакции и
автоматическая миграция версии authority DB без потери старого tombstone.
Пройдены Ruff check/format и Pyright для этих файлов. Общая CI матрица и
интеграция P14/P18/P23 проверяются после объединения веток.

## Открытые ограничения

1. Tombstone обеспечивает **логическое закрытие в этом сервисном пути**.
   `ObservationArchive` остаётся append-only и физически хранит старые байты;
   прямые обращения к нему вне `OperationalStore` обходят этот допуск. До
   реального пилота нужны правила удаления исходных байтов, контроля копий,
   разграничения доступа к самому архиву и проверка легальности хранения.
2. Внешний администратор может заменить **саму** SQLite базу authority старой
   копией. Код сознательно не заявляет защиту от такого отката без внешнего
   доверенного монотонного регистра/контроля копий. Rollback **только bundle**
   с неизменной актуальной authority проверен.
3. SQLite барьер действует, если все пути запуска ревизии и публикации
   используют **одну** authority базу и `start_revision` вызывается до
   изменения engine. Произвольная мутация in-memory engine, внешний job store
   без согласованного барьера или выдача draft вне `publish_answer` не
   покрываются. `revision_guard` читает внешний checkpoint дополнительно, но
   сам по себе не даёт атомарности с другим журналом.
4. Если во время pending job происходит отзыв, epoch меняется, завершение
   старого job fail closed; нужен новый контролируемый путь восстановления
   после проверки текущих источников. Функция не очищает pending автоматически.
5. Встретившиеся в тестах строки и права придуманы. Нет выбранного владельца
   реальных прав, согласованного корпуса и измерения на целевой машине.
